01

Goal

PgSeries delivers TimescaleDB-shape time-series ergonomics on any Postgres 17+ — managed, self-hosted, or laptop — using only pure SQL and PL/pgSQL. The single-file install gives users hypertables, continuous aggregates, columnar compression, and retention policies under the same names and call shapes TimescaleDB users already know, trading the ratio of C-extension columnstores for the reach of "runs anywhere Postgres runs". v0.1 is sized for 10 billion rows in a single series table on a single managed-PG instance.

It is the time-series sibling of PgQue — same install model, same Apache-2.0 license, same anti-extension posture. PgQue's PgQ engine is embedded for the snapshot/tick semantics that continuous aggregates and the job scheduler need.

Architecture

Six interlocking pieces. The hot write path stays inside PG's own row-routing; everything PgSeries-specific runs as a PgQue-scheduled job outside the writer's transaction.

Six pieces

  1. 01
    Time partitioning

    Native PG range partitioning. PgQue pre-creator stays a week ahead. DEFAULT stashes misses; mover job creates the partition and moves rows out within ~200 ms. Zero PgSeries code on the hot path.

  2. 02
    Continuous aggregates

    AFTER STATEMENT triggers feed a PgQue queue plus a data-time invalidation log keyed by (cagg_id, bucket). PgQue tick = batch boundary = materialization watermark. Backdated UPDATE/DELETE correctly re-materializes past buckets.

  3. 03
    Compression

    Cold chunks roll into a parallel _compressed sibling. Segmentby + orderby + parallel typed arrays in TOAST. BRIN minmax_multi_ops on sidecar stats columns. Not a real columnstore — pragmatic workaround.

  4. 04
    Late writes

    The chunk heap stays around as the staging area. Two modes: staging (default; recompression merges back) or error. The previous auto_decompress mode is gone.

  5. 05
    Embedded PgQue

    PgQue's pgque-core ships vendored at pgseries/_pgque/, schema pgseries_pgque. Three uses: cagg invalidation queue, system_jobs runner, staging→recompression signaling.

  6. 06
    Space partitioning (v0.2)

    Catalog supports it from day zero (pgseries.dimension rows with dimension_type); chunk identity is a tuple. v0.1 only writes 'time' rows; add_dimension() exists and returns a v0.2 error.

  7. 07
    Job scheduling

    No PgSeries-specific scheduler. PgQue's ticker model: pg_cron, pg_timetable, or any external driver calling pgque.ticker(). Per-job advisory lock prevents overlapping runs.

04

Scope

In scope v0.1

  • Hypertables (series tables), chunks
  • Retention, compression, recompression policies
  • Continuous aggregates with partial-form storage
  • Real-time aggregation across the watermark
  • Hierarchical caggs (fixed-width and calendar-width buckets)
  • Columnar compression (segmentby + orderby, FOR + dict + lz4)
  • time_bucket(), time_bucket_gapfill() (single-group-key)
  • first() / last() aggregates with combinefuncs
  • BRIN minmax_multi_ops data skipping
  • Job scheduler via PgQue ticker
  • show_chunks / drop_chunks / refresh_continuous_aggregate
  • pgseries_information views
  • Migration: per-chunk parallel pg_dump + adopt_partitioned_table()
  • Three roles: reader / writer / admin

Out of scope v0.1 or never

  • Bit-level codecs (Gorilla, delta-delta, simple-8b)
  • Custom planner / executor nodes
  • True columnar storage
  • Distributed hypertables
  • Tiered storage to object storage
  • Promscale-style ingest caggs
  • Space partitioning (add_dimension) — v0.2
  • Hypertable → series_table in-place converter
  • FK cascades into source tables — v0.2
  • PostgreSQL 16 or older
  • Direct-to-leaf-partition writes — revoked in v0.1

Partial / lossy items: hyperfunctions (use PG built-ins instead), approximation sketches (hll only; tdigest deferred), multi-group time_bucket_gapfill, lossless float compression (Gorilla unavailable), and certain cagg select-list shapes (HAVING, GROUPING SETS/ROLLUP/CUBE, window functions, aggregates without combinefuncs).

05

Decisions

Eight architectural decisions documented in the spec, in spec order.

  1. Embed PgQue, don't depend on it. keeps the install single-file, single-transaction; avoids "install pgque first" coordination across providers.
  2. DEFAULT-partition stash, not a BEFORE INSERT trigger that does DDL. ATTACH PARTITION conflicts with the parent's running INSERT lock; tuple routing is resolved before BEFORE fires; on a multi-row COPY only the first row could possibly succeed mid-statement.
  3. PgQue tick + data-time invalidation log, two structures, not one. the tick alone is monotonic in transaction time, not data time. Backdated DML would silently drift a tick-only design.
  4. Cagg storage is partial-form by default, not finalized. a UNION of finalized values + raw rows produces wrong results for avg, stddev, percentile_*, and DISTINCT aggregates around the watermark.
  5. Two siblings per chunk, not three. a three-way UNION ALL exposes three relations to the planner with separate stats; chunk exclusion doesn't cross the union boundary. Two branches keep the planner happy and one branch is empty in steady state.
  6. Pre-installed CHECK constraint before ATTACH. ATTACH PARTITION otherwise scans the new child to validate the partition constraint, which on a non-trivial compressed sibling can blow past a 1s lock timeout, leaving the parent missing a range.
  7. BRIN minmax_multi_ops, not plain minmax_ops. heap row order on the compressed sibling is segmentby-then-orderby, not time-monotonic; plain minmax widens to whole-chunk ranges and skips nothing. Multi-minmax keeps disjoint intervals per range.
  8. PG 17 floor. greenfield projects can pick a modern PG; PgSeries leans on PG 17 partitioning ergonomics (MERGE, MERGE/SPLIT PARTITION opportunistically) for simpler code.
06

Open questions

Decisions in flight before v0.1 ships

  • Default chunk size: time-based (1 day), row-based (~3 × 107), or adaptive? At the 1010-row target the two converge on ~1 day.
  • Segment row count default. 1 000 to start; revisit after benchmarks.
  • Lossy float requantization: opt-in per column at table creation, or per compression policy?
  • Table abstraction name: series_table (default) vs hypertable (trademark check) vs other.
  • pgseries_information view names: mirror existing time-series conventions or differentiate?
  • Cagg select-list shapes: which of HAVING / ROLLUP / window functions can be lifted in v0.2 with a specified recombination rule?
  • Embedded-PgQue schema collision: is pgseries_pgque distinctive enough?
  • v0.2 add_dimension API shape: hash partitions only, or hash + range?
  • materialized_only cagg storage: when (if ever) is it the better default?
  • DEFAULT-partition mover lag SLA. v0.1 target: ≤200 ms p95. Worth pinning at acceptance time?
  • Future: PgSeries-as-default-storage + DuckDB / Apache Arrow as acceleration on installs that allow extensions.
07

Risks & failure modes

Past 1010 rows on a single instance

  • Cagg refresh latency on dense backfills — invalidation log gets dense; tunable via coalesce_interval and the refresh window.
  • PL/pgSQL compression throughput per chunk — group-by-segmentby costs O(rows/chunk). 27M rows/chunk benchmarks in minutes; >108 rows/chunk would not. add_dimension (v0.2) is the escape hatch.

Watch-outs at v0.1's scale

  • Segmentby cardinality > ~104 per chunk collapses ratio to ~1.5×. add_compression_policy() warns at 50 000.
  • Float-heavy workloads compress 1.5–2.5× without lossy requantization. Bit-level codecs (Gorilla) are not feasible in PL/pgSQL.
  • Direct-to-leaf-partition writes would silently break cagg invalidation. Closed in v0.1 by revoking direct-child INSERT.
  • Plan-cache invalidation after a compression swap — pooled clients with prepared statements replan on first use post-swap.
  • FK cascades into the source table don't fire statement triggers. Rare in time-series schemas; v0.2 problem.

Acceptance criteria

Each criterion is either a CI-checkable artifact or a benchmark with a reportable number. v0.1 doesn't ship until every item is green on PG 17 and PG 18.

  • Install. \i pgseries.sql installs cleanly on stock PG 17 and PG 18 in a single transaction. Bundle includes pgque-core into a pgseries_pgque schema.
  • Plan-shape regression test. pgTAP test asserts partition pruning + BRIN minmax_multi_ops segment skipping + zero Function Scan on unpack_segment for skipped partitions.
  • Stats hygiene. After a compression swap, pg_class.reltuples on the compressed sibling matches seg_row_count sum within 1 % before any user query.
  • Smoke test. RDS, Aurora, Cloud SQL, Supabase, Neon, Crunchy Bridge with PG 17+; 107 rows over ≤10 minutes; 95 p job completion within 2× schedule_interval.
  • Scale benchmark. Single self-hosted PG 18, 1010 rows over 30 days, all policies running. Reference hardware: local NVMe, ~128 GiB RAM, modern many-core x86.
  • Compression benchmark. NYC taxi + devops-metrics, ratio + scan latency on PgSeries vs uncompressed PG vs pg_timeseries (Citus columnar). Per-column-type breakdown.
  • Cagg correctness. Out-of-order writes within refresh_lag reconcile by next refresh; out-of-window writes appear in cagg_lag. Backdated-DML test: 2022-row UPDATE re-materializes the 2022 bucket.
  • Aggregate correctness across watermark. avg, stddev, percentile_cont on a stream straddling the watermark match a direct query against the source within numeric tolerance.
  • Default-partition catch. Pre-creation off; mover creates the partition + moves rows; nothing left in …_default after one tick.
  • Compressed write path. error mode raises; staging mode round-trips through the recompression merge.
  • Read-only enforcement. Two triggers (row-level + statement-level for TRUNCATE) raise; revoke denies before the trigger fires.
  • Compression swap. lock_timeout retry test under contention; no orphaned partitions, no half-detached state.
  • Chunk lease vs retention. Retention against an actively compressing chunk waits or skips; never deadlocks. Retention against a chunk overlapping a cagg refresh window also defers.
  • Job overlap prevention. Two ticker drivers running concurrently never run the same job body twice in parallel.
  • Space-partition catalog forward-compatibility. v0.1 catalog round-trips a v0.2 dimension_type = 'space_hash' row without schema migration.
  • Red/green TDD for pgseries-api; pgseries-core covered by regression tests against PG 17 and PG 18.
